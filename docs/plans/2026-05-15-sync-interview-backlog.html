RFC · Implementation plan

Sync /interview ↔ /backlog

Pivot JSON entre les deux skills + enrichissement codebase par phase, pour que /backlog génère des tâches atomiques complètes sans devinette ni perte de contexte.

« Trouve le meilleur moyen pour ne perdre aucun contexte entre /interview et /backlog, que le workflow soit ultra smooth. Backlog doit avoir assez d'intel pour générer des tâches atomiques mais aussi complètes — qu'un agent qui prend la task ne tombe pas dans des erreurs d'archi (ex. dupliquer une fonction qui existe déjà). »
TL;DR. /interview écrit un bundle JSON (Decisions + change_kind + target hints) à côté de plan.html. /backlog consomme ce bundle, génère des tâches atomiques liées par decision_refs[], et enrichit chaque tâche via 1 Explore agent par phase (Reuse / Follow / Avoid / Tests). Effort total : I4 / V8, étalé sur 3 skills.

Le problème

Aujourd'hui, le bouton "Copy as backlog prompt" de plan-html émet un markdown plat (Decisions verbatim + liste libre de Steps). Au copier-coller dans /backlog, on perd plusieurs canaux d'information.

❌ Handoff actuel — markdown plat
  • change_kind de l'interview perdu
  • Projet Linear cible deviné
  • Linkage Step → Decision perdu
  • DoD par task perdu (la Verification est au niveau Decision, pas Step)
  • WHERE par task deviné
  • « autres apps internes » → liste implicite
  • Aucune anti-duplication face au code existant
vs
✅ Handoff cible — bundle JSON
  • Bundle JSON pivot, généré par plan-html
  • Decisions verbatim + change_kind + target hints
  • /backlog mappe Decision → tâches atomiques
  • Chaque task porte decision_refs[] (traçabilité)
  • Check de couverture (∀ Decision, ≥1 task)
  • 1 Explore agent par phase → dossier de réutilisation
  • Description enrichie : Reuse / Follow / Avoid / Tests
Avant ↔ après — ce qui transite entre les skills

Structure du bundle

backlog-bundle.json
├── schema_version : "1"
├── source
│ ├── kind : "interview"
│ ├── slug : "multi-services-isolation"
│ └── change_kind : "breaking-brownfield"
├── target
│ ├── linear_project_hint : "NextNode Infrastructure"
│ ├── linear_team_hint : "INT"
│ └── repo_path_hint : "packages/infrastructure"
├── decisions[] — 6 champs verbatim closure
│ └── { id, theme, fact, mechanism, edge, rejected, order, verification }
├── open_facts
│ └── apps_to_migrate : ["monitoring"]
└── freeform : "..."
Schéma du pivot — pas de phases, pas de tasks (c'est /backlog qui les fabrique)

Décisions (5)

D1schema
Bundle JSON comme pivot, pas markdown plat
Le handoff /interview → /backlog passe par un fichier backlog-bundle.json structuré. Le markdown plat actuel reste accepté en fallback pour les paste manuels.
Mechanism
/interview §3.5 écrit docs/interviews/<slug>/backlog-bundle.json. plan-html ajoute un bouton « Copy as backlog » sur le bloc next-steps qui émet le même JSON dans le presse-papier.
Edge
Touche : § 3.5 de /interview, bouton du next-steps de /plan-html. Ne touche pas : le schéma 6 champs des Decisions, la closure UI, le rendu HTML.
Rejected
Markdown plat enrichi (devinette inévitable) · YAML (un format de plus, pas de gain) · Direct read de state.json par /backlog (couplage trop fort, casse le paste manuel).
Order
Première brique. Les 4 autres décisions dépendent de la forme du bundle.
Verification
Après /interview sur un slug réel : cat docs/interviews/<slug>/backlog-bundle.json | jq '.decisions | length' retourne N. jq '.source.change_kind' retourne la valeur captée en discovery.
D2scope
/interview reste focus Decisions, /backlog fait le split phases+tasks
L'interview ne produit jamais de phases ni de tasks. Le bundle porte uniquement les Decisions résolues. C'est /backlog qui décompose Decision → tasks atomiques et qui groupe en phases.
Mechanism
Le bundle n'a pas de champ phases ni tasks. /backlog Phase 3 fait le mapping Decision → 1..N tasks en appliquant ses règles d'atomicité existantes (pas de "et" / "+" / "," dans les titres). Le phase grouping vient de Decision.order.
Edge
Touche : rien dans /interview (juste l'écriture du bundle). Ne touche pas : le UX closure, les 3 rounds (discovery / grilling / closure).
Rejected
UI inline dans la closure pour valider phases+tasks (alourdit /interview sans valeur ajoutée) · Pré-split côté /interview (mélange responsabilités).
Order
Concurrent avec D1.
Verification
jq 'has("phases")' bundle.json → false. jq 'has("tasks")' bundle.json → false. Le bundle ne contient que decisions + métadonnées.
D3fidelity
Enforce decision_refs[] sur chaque task + check de couverture
Chaque task générée par /backlog doit référencer ≥1 Decision du bundle (decision_refs[]). Avant Phase 4, vérifier que chaque Decision est couverte par ≥1 task. Sinon : générer la task manquante ou avorter.
Mechanism
Nouvelle règle dans /backlog Phase 3, non négociable : ∀ task t : |t.decision_refs| ≥ 1 et ∀ Decision D : ∃ t : D ∈ t.decision_refs. La preview Phase 4 affiche une colonne "Decisions couvertes" et flag rouge sur les Decisions orphelines.
Edge
Touche : /backlog Phase 3 (génération) et Phase 4 (preview). Ne touche pas : le format tasks.json côté worker, la création Linear elle-même.
Rejected
Couverture optionnelle / best-effort (perd la garantie) · Validation user-in-the-loop (déjà rejeté en D2).
Order
Après D1 (bundle existe). Avant D4 (l'enrichment se branche sur les tasks déjà décomposées).
Verification
Sur un bundle test à 12 decisions : preview affiche couverture 12/12. Supprimer manuellement les decision_refs d'une task → preview affiche 11/12 + flag rouge sur la Decision orpheline.
D4enrichment
Codebase enrichment par phase, pas par theme ni par task
Nouvelle sous-étape Phase 3.5 : pour chaque phase, lancer un seul Explore agent sur la surface union de toutes ses tasks. Le résultat (dossier de phase) est partagé entre toutes les tasks de la phase.
Mechanism
Pour chaque phase : union des where[] de ses tasks → 1 Explore agent prompté avec change_kind + les Decisions couvertes (Mechanism + Edge) + la surface. Sortie : dossier {reuse[], follow[], avoid[], tests[]}. Chaque task pioche ses entrées pertinentes via match where[] / decision_refs.
Edge
Touche : /backlog nouvelle Phase 3.5. Ne touche pas : /interview, /plan-html, le worker create_issues.py.
Rejected
1 Explore par theme (cross-phase, signal éclaté) · 1 Explore par task (~25 agents, trop coûteux, redondant) · 0 enrichissement (problème non résolu, c'est le cœur du fix).
Order
Après D3 (couverture validée). Avant D5 (le dossier doit exister avant d'être persisté).
Verification
Sur un bundle test à 5 phases : exactement 5 Explore agents lancés (vérifiable dans le log). Description finale d'une task contient ≥1 entrée Reuse pointant vers file:line existant.
D5persistence
Dossier de phase persisté à côté de tasks.json
Le dossier de phase est écrit sur disque dans phase-contexts/phase-N-<name>.md. Les agents qui prennent les tasks le lisent en plus de leur issue Linear pour un contexte partagé entre tâches sœurs.
Mechanism
Layout : /tmp/claude/backlog-<slug>-<ts>/phase-contexts/phase-1-<name>.md, un fichier par phase. Markdown, lisible humain + agent. Référencé dans la description de chaque issue Linear : "Phase context: <path>".
Edge
Touche : /backlog Phase 3.5 (écriture du dossier) et Phase 4 (référence dans la description). Ne touche pas : le contenu de tasks.json.
Rejected
Dossier en mémoire seulement (perdu après run, pas de reprise) · Dossier intégré dans tasks.json (duplication N fois, alourdit l'issue Linear).
Order
Dernière. Toutes les autres doivent exister.
Verification
Après run : ls phase-contexts/ liste N fichiers (= nombre de phases). Chaque issue Linear contient une ligne "Phase context: /tmp/claude/.../phase-N-*.md".

Forme du dossier de phase

Markdown, ~30-60 lignes par phase. Lu par les agents implémenteurs.

# Phase 1 — Schema & types
# Decisions couvertes: D1, D2, D3
# Surface: packages/infrastructure/src/config/{types,parser,validation}.ts

## Reuse
- parseManagedServices() @ config/parser.ts:55 — mimer la structure pour parseCustomServices()
- ManagedServiceConfig @ config/types.ts:80 — extraire un type pivot avant d'ajouter AppServiceConfig
- SERVICE_DEFINITIONS @ services/registry.ts:12 — source de vérité reserved names, ne PAS hardcoder

## Follow pattern
- Validators sidecars sous config/validation/services/*.ts — un fichier par kind, signature validateXxx(input): Result<T, ValidationError>
- toml-key.regex.ts:18 pour la regex de validation TOML key

## Avoid
- Ne pas ajouter de logique deploy ici (D1.edge)
- Ne pas dupliquer la regex TOML — voir utils/toml.ts:18
- Ne pas casser ServicesConfig existant (breaking change réservé à D12)

## Test scaffolding
- Fixtures TOML sous __fixtures__/configs/*.toml
- Helper parseFixture() @ test/utils.ts:9
