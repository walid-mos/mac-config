Le skill /improve de shadcn

Un advisor senior read-only : il audite le repo avec ton meilleur modèle et écrit des plans que des modèles moins chers exécutent.

Demande — « Check le skill /improve de shadcn, fais-moi une explication de ce que j'y gagnerais à l'utiliser, les features… »

shadcn/improve sépare l'intelligence de l'exécution : le modèle cher (Fable/Opus) fait le recon, l'audit 9 catégories, le tri des faux positifs et la rédaction de specs auto-portantes dans plans/ ; un modèle cheap (Sonnet/Haiku) les exécute dans un worktree isolé, et l'advisor review le diff comme un tech lead. Tu y gagnes un backlog d'améliorations persistant, vérifié et priorisé par levier — pas une liste de suggestions jetables. Il ne touche jamais ton code lui-même.

01Le concept : le plan est le produit

Le skill n'implémente jamais rien. Il produit des specs assez bonnes pour qu'un modèle plus faible, sans aucun contexte de session, exécute sans improviser.

L'argument économique : l'intelligence d'un modèle haut de gamme compte là où elle compose — comprendre le codebase, juger ce qui vaut le coup, spécifier. L'exécution mécanique d'une spec précise, un modèle cheap la fait aussi bien. /improve matérialise cette frontière en fichiers markdown : n'importe quel agent (ou humain) peut les reprendre.

Toi + modèle fort/improve · advise
plans/001-….mdspecs auto-portantes
Modèle cheapimplémente · teste · ship
l'intelligence en amont, l'exécution en aval — le plan est l'interface
Règle dure Seules écritures autorisées : plans/. Jamais d'édition de source, jamais de commande qui mute le working tree, jamais de secret reproduit (path + type seulement). Si tu lui demandes d'implémenter, il refuse et pointe le plan.

02Le pipeline interne

Cinq phases, dont une de vetting que la plupart des skills d'audit n'ont pas.

Reconstack · conventions · cmds
Auditsubagents ∥ × 9 cat.
Vetrelit chaque file:line
Prioritizeimpact ÷ effort × confiance
Plansplans/ + index
recon → audit parallèle → vetting anti-faux-positifs → tri par levier → specs

Recon extrait les commandes build/test/lint exactes du repo — elles deviennent les portes de vérification de chaque plan. Il ingère aussi les docs d'intention (ADRs, CONTEXT.md, DESIGN.md, PRD) pour ne pas re-signaler des tradeoffs déjà décidés.

Audit fan-out des subagents read-only en parallèle sur neuf catégories : correctness, sécurité, perf, couverture de tests, dette technique, dépendances & migrations, DX, docs, et direction (suggestions de features — chacune doit citer une preuve dans le repo, zéro idea-slop). Chaque finding porte file:line, impact, effort S/M/L, risque du fix et confiance.

Vet est la phase différenciante : les subagents sur-rapportent, donc l'advisor rouvre lui-même chaque emplacement cité avant de te montrer quoi que ce soit. Les faux positifs tombent, les attributions fausses sont corrigées, et les rejets sont enregistrés dans l'index pour ne pas revenir au prochain run (ex. réel : https_proxy flaggé SSRF → rejeté « by-design, convention standard »).

Prioritize te présente la table triée par levier ; tu choisis (« plan 1, 3 et 5 »), il n'écrit jamais 30 plans que personne n'a demandés. Les findings « direction » sont présentés à part — des options à peser, pas des bugs à ranker.

03Les variantes d'invocation

Une commande, dix modes — du quick pass au cycle complet audit → exécution → réconciliation.

/improve deepExhaustif : tout le repo, ≤8 subagents, toutes catégories, y compris les items LOW-confidence.

04Ce qui rend les plans exécutables par un modèle faible

Trois propriétés structurelles, écrites pour « le plus faible exécuteur plausible ».

Auto-portant

contient
paths exacts · extraits du code actuel · conventions du repo avec fichier exemplaire · commandes vérifiées au recon
interdit
« comme discuté plus haut »

Portes de vérification

chaque étape
se termine par une commande + sortie attendue
done criteria
machine-checkables, jamais « ça marche correctement »

Bornes dures

scope
in-scope / out-of-scope explicites, même pour ce qui « a l'air lié »
STOP conditions
« si X, arrête et rapporte » — jamais d'improvisation

Chaque plan stampe le commit SHA contre lequel il a été écrit ; l'exécuteur lance un drift check mécanique (git diff --stat <SHA>..HEAD -- <scope>) avant de toucher quoi que ce soit. Le template impose aussi un test plan (modelé sur un test existant du repo), des notes de maintenance, et le workflow git du repo.

  • plans/
    • README.md INDEX — ordre d'exécution, graphe de dépendances, statuts (TODO/DONE/BLOCKED/REJECTED), findings rejetés
    • 001-fix-n-plus-one.md PLAN
    • 002-extract-shadow-config.md PLAN

05La boucle fermée : execute, reconcile, issues

Les plans ne sont pas fire-and-forget — c'est ce qui distingue le skill d'un générateur de TODO.

graph LR P[plan NNN] --> D[Executor cheap
worktree isolé] D --> R{Review advisor} R -- criteria OK, scope clean --> A[APPROVE
merge = ta décision] R -- gaps corrigeables --> V[REVISE
max 2 rounds] V --> D R -- STOP / scope violé --> B[BLOCK
plan raffiné]

La review d'execute ne fait pas confiance au rapport de l'exécuteur : l'advisor re-lance chaque done criterion dans le worktree, vérifie la conformité de scope au diff près, lit le diff complet contre l'intention, et audite les nouveaux tests (un test qui n'asserte rien passe pnpm test et ne prouve rien). Les déviations documentées sont jugées sur le fond ; les déviations silencieuses échouent la review. Il ne merge, push ni commit jamais sur ta branche.

reconcile traite l'entre-sessions : spot-check des DONE sur le HEAD courant, investigation des BLOCKED avec réécriture du plan autour de l'obstacle, refresh des TODO driftés, retrait des findings corrigés indépendamment.

06Ce que tu y gagnes — et les limites

Mappé sur ton setup : tu as déjà /architecture, /code-review et /simplify — /improve ne les remplace pas, il couvre l'étage au-dessus.

✅ Gains réels

  • Économie de tokens structurelle : Fable/Opus pour juger, Sonnet/Haiku pour taper. Sur un backlog de 5–10 plans, l'écart de coût est significatif.
  • Backlog persistant : plans/ + index avec statuts survit aux sessions. Tes audits actuels (/architecture) produisent un rapport jetable ; ici les findings rejetés sont mémorisés et ne reviennent pas.
  • Vetting anti-bruit : la phase Vet relit chaque file:line cité avant de te montrer la table — moins de faux positifs que les audits subagents bruts.
  • 9 catégories en un run, dont « direction » (features ancrées dans le code, pas du brainstorm générique) — aucun de tes skills actuels ne couvre ça.
  • Read-only garanti : auditable sur un repo client NextNode sans risque de mutation ; exécution confinée en worktree jetable, merge toujours manuel.
  • Interopérable : plans en markdown pur + --issues → exploitables par Cursor, Codex, un humain, ou un agent cloud.

⚠️ Limites

  • Coût d'entrée : un run standard = recon + ≤4 subagents + vetting ; deep = ≤8. Sur un petit repo, /improve quick suffit — le mode complet est calibré pour des codebases conséquentes.
  • Friction sur micro-fix : il refuse d'implémenter directement, même un one-liner. Pour « corrige ce bug », ton workflow normal reste plus court.
  • Recouvrement partiel avec /code-review (improve branch vs review de diff) et /architecture (catégorie tech-debt) — choisis par intention : ship une PR → /code-review ; construire un backlog → /improve.
  • Pollution du repo : plans/ vit à la racine. Sur un repo partagé, à gitignorer ou committer en connaissance de cause.
  • execute requiert un host capable de spawner des subagents en worktree (Claude Code ✅, d'autres agents pas forcément).

07Verdict et installation

À adopter si tu veux un backlog d'améliorations entretenu sur tes repos NextNode : un /improve périodique + reconcile donne une vue priorisée et vérifiée de la dette, et execute délègue le mécanique à Sonnet/Haiku pendant que tu review. À ignorer pour les fixes ponctuels — tes skills existants y sont plus directs. Le pattern plan-template (extraits du code actuel, portes de vérification, STOP conditions, drift check par SHA) vaut aussi le vol pour tes propres skills de handoff.

  • → Installer : npx skills add shadcn/improve
  • → Premier run cheap sur un repo réel : /improve quick, puis sélectionner 2–3 findings.
  • → Tester la boucle complète : /improve execute 001 avec Sonnet, juger la qualité de la review.
  • → Décider du sort de plans/ (committer vs gitignore) avant de l'adopter sur les repos partagés.
