Automatiser la génération de tweets et threads en anglais à partir du travail dev quotidien, à partir d'une description libre ou de screenshots, dans la voix du user, sans hype ni guru.

TLDR

Skill /tweet (doctrine éditable) + subagent tweet-drafter (boucle d'exécution avec auto-critique). Le skill résout l'input et délègue au subagent qui charge 3 fichiers de doctrine (voice, formats, algo), draft 5 candidats variés, score sur 5 axes, retourne 2 finalistes copy-paste ready. Tweets en anglais, capitalisation standard, em-dash banni à tous les niveaux du stack.

Decisions

D1 Skill + Agent (les deux)
Split clair : skill = doctrine éditable en markdown (voice / formats / algo), agent = boucle d'exécution avec auto-critique. Pas un seul des deux, les deux.
Mechanism
Le skill résout l'input et spawn le subagent. Le subagent recharge les 3 fichiers de doctrine à chaque run, donc toute évolution de voix se propage sans toucher au prompt de l'agent.
Edge
Skill appelable seul pour un draft brut. Agent appelable directement (sans /tweet) pour un one-shot.
Rejected
Skill-only (pas d'itération), agent-only (les règles dérivent dans le prompt et ne sont plus éditables comme une doc).
Verification
Le skill charge bien voice/formats/algo avant de spawn. L'agent refuse si un fichier doctrine manque.
D2 Output ENGLISH (pas français)
Tweets sortent en anglais par défaut. Le user est français mais cible le public dev international. Français uniquement en aparté entre parenthèses si naturel.
Mechanism
Règle "OUTPUT IS ENGLISH" en tête de voice.md. Examples, hooks, banned/approved expressions tous réécrits en anglais. Override possible si user demande explicitement un tweet FR.
Edge
Mots français OK en aparté entre parenthèses (ex : noms de villes, citation client), pas dans le body.
Rejected
French-first (audience plafonnée), bilingue dans le même tweet (dilue la voix et le branding).
Verification
Tous les good-examples de voice.md et formats.md sont en anglais. Hook patterns en anglais.
D3 Sentence-case (pas lowercase shitpost)
Capitalisation standard : première lettre du tweet en majuscule, "I" en majuscule. Lowercase autorisé seulement en aparté casual ou one-liner punchline, jamais comme default.
Mechanism
Section "Style tics" de voice.md enforce sentence-case. Examples réécrits avec capitales correctes après le pushback du user en cours de session.
Edge
Final period optionnel sur un tweet court punchy. Mandatory dans les threads ou dès qu'il y a 2+ phrases.
Rejected
Lowercase first letter comme signature (lu comme négligé par les CTO de PME/ETI ciblés à terme, pas comme cool).
Verification
Tous les good-examples capitalisent normalement. Refs (SpottedYou, Picaro_11) capitalisent normalement aussi.
D4 Input resolution explicite
Ordre strict : $ARGUMENTS → screenshots du turn courant → proposition explicite basée sur la session courante avec confirmation → question ouverte. Jamais de scrape silencieux des turns précédents.
Mechanism
Phase 1 de SKILL.md walk l'ordre, stop au premier hit, ne combine jamais. L'agent reçoit un bundle pré-résolu et refuse si vide.
Edge
Si la session a un signal "on vient de shipper X", proposer explicitement et attendre confirmation. Jamais d'assomption muette.
Rejected
Fallback silencieux sur "last 1-3 user turns" (pioche du contenu sans rapport, invente du contexte, comportement opaque).
Verification
/tweet sans args et sans screenshot doit déclencher la proposal-ou-question, pas un guess.
D5 Em-dash hard ban
Caractère — banni dans toute sortie. Remplaceurs autorisés : hyphen, virgule, parenthèses, retour à la ligne. Règle non-négociable.
Mechanism
Ban écrit dans : SKILL.md hard rules, voice.md banned expressions ("HARDEST BAN"), tweet-drafter.md hard bans, step 4 self-critique "HARD FAIL si em-dash → redraft".
Edge
Em-dash toléré uniquement dans les énoncés de règle (qui doivent montrer le caractère) et dans les contre-exemples labellés "BAD" (qui montrent ce qu'il ne faut pas faire).
Rejected
Allowing em-dash "avec parcimonie" (les LLMs en anglais en mettent partout, drift inévitable).
Verification
Grep — dans tweet/ retourne uniquement règles + BAD examples. Zéro dans les templates ou good examples.
D6 Boucle 5 → score → 2
L'agent draft 5 angles distincts (outcome / lesson / cost / story / hot-take), score chaque candidat sur 5 axes (slop / dwell / bookmark / outrage / truth), kill ce qui passe sous le seuil, retourne les 2 meilleurs avec rationale d'une ligne.
Mechanism
Step 3 génère 5 angles forcés différents. Step 4 score 1-5 par axe, total /20. Kill si total < 14 ou n'importe quel axe < 3 ou em-dash présent ou specific inventé. Redraft si < 2 survivent.
Edge
Si input trop mince, retourner UN candidat labellé "best effort, need X" avec ask concret (nombre, screenshot, résultat). Jamais de slop pour atteindre 2.
Rejected
Single-shot draft (pas d'itération), 3+ finalists (décision fatigue côté user, dilue le choix).
Verification
Output format strict : exactement 2 blocs === FINALIST N === avec rationale d'une ligne. Tests : run /tweet avec un swap d'outil, vérifier que les 2 finalistes varient d'angle.

Risks

Risk
Severity
Mitigation
Voice drift : les règles en markdown se contredisent au fil des éditions, le drafter produit des choses incohérentes.
med
Re-lire voice.md complet une fois par mois. Si une règle est éditée, vérifier que les good-examples respectent encore.
Em-dash leak : un futur draft d'agent ou un edit de doctrine introduit un em-dash dans un template ou un good-example.
high
Ajouter un hook PostToolUse sur Write/Edit qui grep — dans skills/tweet/ et agents/tweet-drafter.md, alert si hors règles/BAD.
X algo changes : la doctrine algo.md vieillit, les signaux ne reflètent plus le scoring réel.
low
Marquer algo.md avec la date de référence (mai 2026). Re-check tous les 6 mois ou quand X annonce un changement majeur.
Self-critique trop laxiste : le drafter retourne 2 finalistes faibles parce que le seuil 14/20 est trop bas.
med
Après 2 semaines d'usage, regarder quels finalistes le user a réellement publiés vs ignorés. Ajuster le seuil ou les axes.
Hallucination de specifics : le drafter invente un nombre ou un outcome non présent dans l'input.
high
Truth-check est déjà un axe de scoring avec HARD FAIL. Si une hallucination passe quand même, ajouter le cas exact en BAD example dans voice.md.
