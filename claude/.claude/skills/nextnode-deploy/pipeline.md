# Pipeline Architecture

## Workflows

Three reusable workflows — callers choose one based on `type` (no runtime routing in YAML):

### `publish-package.yml` (type=package)

```
plan → quality (matrix) → publish (semantic-release)
```

- Publish only runs on `main` branch and when `plan.outputs.publish == 'true'`
- Uses `semantic-release` via `pnpm exec` (plugins come from `@nextnode-solutions/standards` deps)
- After publish: runs `publish-result` command to parse output and write summary
- Requires `NEXTNODE_APP_ID`, `NEXTNODE_APP_PRIVATE_KEY`, `NPM_TOKEN` secrets
- Does NOT pass `PIPELINE_ENVIRONMENT` — the CLI auto-resolves environment to `'none'` when `type=package`

### `deploy.yml` (type=app — Hetzner future)

```
plan → quality (matrix with prod-gate if prod) → deploy (stub)
```

- Input: `environment: development | production` (required)
- Currently a stub — will deploy to Hetzner in the future

### `deploy-static.yml` (type=static — Cloudflare Pages)

```
plan → quality (matrix with prod-gate if prod) → deploy (Cloudflare Pages)
```

- Input: `environment: development | production` (required)
- Deploy step: `pnpm build` then calls the `deploy-cloudflare-pages` composite action
- `production=true` flag on deploy action when `environment=production` (publishes to `--branch=main`, otherwise `--branch=preview-{run_id}`)
- Requires `CLOUDFLARE_ACCOUNT_ID`, `CLOUDFLARE_API_TOKEN` secrets

## The `environment` input

Both `deploy.yml` and `deploy-static.yml` are generic — the caller invokes them twice (once per env) from two thin caller-repo workflows:

```yaml
# caller-repo/.github/workflows/deploy-dev.yml
jobs:
  pipeline:
    uses: NextNodeSolutions/core/.github/workflows/deploy-static.yml@main
    with:
      environment: development
    secrets: inherit

# caller-repo/.github/workflows/deploy-prod.yml
jobs:
  pipeline:
    uses: NextNodeSolutions/core/.github/workflows/deploy-static.yml@main
    with:
      environment: production
    secrets: inherit
```

The CI passes the workflow's `environment` input to the `plan` command via `PIPELINE_ENVIRONMENT` env var.

## Quality matrix

Generated by `buildQualityMatrix(scripts, project, pipeline)` — `pipeline` is `{ environment, developmentEnabled }`:

| Task       | Condition to include                                   | Command                                                                            |
| ---------- | ------------------------------------------------------ | ---------------------------------------------------------------------------------- |
| `lint`     | `scripts.lint` is not false                            | `pnpm {lint}` OR `pnpm turbo run {lint} --filter={filter}`                         |
| `test`     | `scripts.test` is not false                            | `pnpm {test}` OR `pnpm turbo run {test} --filter={filter}`                         |
| `prod-gate`| `environment=production` AND `developmentEnabled=true` | `cd .infra/packages/infrastructure && pnpm exec tsx src/index.ts prod-gate`        |

Empty matrix → skip sentinel (`{ id: 'skip', cmd: 'echo skipped' }`). `build` never appears in the quality matrix — it only runs in publish/deploy jobs.

## prod-gate task

- Implemented in `prod-gate.ts` as a CLI command (`tsx src/index.ts prod-gate`)
- Calls GitHub API `GET /repos/{repo}/actions/runs?head_sha={sha}` and looks for a run with path `.github/workflows/deploy-dev.yml` (caller repo convention) with `status=completed` + `conclusion=success`
- When present in the quality matrix, the quality job checks out `.infra` too (sparse-checkout of `packages/infrastructure`) via `infra: ${{ needs.plan.outputs.has_prod_gate }}` on the setup action
- Requires `actions: read` permission (declared at workflow level) and `GH_TOKEN` env var (injected on every matrix task — harmless for lint/test)

## Cloudflare Pages composite action

Located at `.github/actions/deploy-cloudflare-pages/action.yml`. Wraps `cloudflare/wrangler-action@v3` with `pages deploy`:

| Input          | Required | Description                                            |
| -------------- | -------- | ------------------------------------------------------ |
| `directory`    | Yes      | Path to built static assets (e.g. `dist`)              |
| `project-name` | Yes      | Cloudflare Pages project name                          |
| `production`   | No       | `"true"` → `--branch=main`, else `--branch=preview-{run_id}` |
| `account-id`   | Yes      | Cloudflare account ID                                  |
| `api-token`    | Yes      | Cloudflare API token with Pages edit permission        |

Outputs `url` (the deployment URL).
