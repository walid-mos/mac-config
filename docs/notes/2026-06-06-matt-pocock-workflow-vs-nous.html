Le workflow de Matt Pocock — et ce qui nous sépare

Reconstruction du process de travail AI-coding de Matt Pocock (Total TypeScript / AI Hero) à partir de son repo mattpocock/skills et d'aihero.dev, puis comparaison ligne à ligne avec notre propre workflow /interview → /backlog → /track → /next.

Demande : « Profile les skills de Matt Pocock, fais-moi un retour exact de son workflow de travail, et notamment les différences avec le nôtre. Utilise /html, fais le maximum de schémas. »
Matt Pocock — orange, GitHub-natif Nous — teal, plan.json + progress.db

En une phrase : on a construit, chacun de son côté et sans se concerter, le même squelette — griller avant de coder, découper en tranches verticales, encoder le process en skills markdown, verrouiller par des hooks déterministes — mais Pocock optimise pour le partage et la légèreté (PRD en prose → issues GitHub), nous pour le contrôle et la traçabilité machine (plan.json versionné + base progress.db + critique de couverture).

Pocock est GitHub-centric et prose-first : l'issue GitHub est à la fois le plan et l'état. Nous séparons strictement spec (plan.json, dans le repo, versionné, validé par read_plan.py) et état (~/mizraj/<slug>/progress.db, hors repo, machine d'état SQLite). Là est le clivage structurant.

01Deux philosophies, un même refus du « vibe coding »

Pocock résume sa posture par le spectre « YOLO vs OH NO » : ni l'autonomie totale ni le micro-management ne livrent du logiciel — la voie du milieu est de designer le process, l'encoder en skills, et laisser l'agent rouler sur les rails posés. Notre doctrine part du même refus mais s'ancre dans des règles dures non-négociables.

Matt Pocock

  • « Fundamentals first » — Brooks, Fowler, Ousterhout, Pragmatic Programmer : l'ingénierie classique prime sur les techniques « AI-spécifiques ».
  • YOLO ↔ OH NO : la valeur est dans la voie médiane outillée.
  • 4 modes d'échec ciblés : désalignement verbosité qualité entropie d'archi.
  • Skills : 1 fichier .md, 50–200 lignes, lisible en 90s, sans DSL, composables, model-agnostic, publics (MIT).
  • Optimise pour le partage (repo open-source, réutilisable par toute équipe).
vs

Nous

  • Greenfield HARD RULE : zéro fallback, zéro migration, zéro compat. Une seule voie, la bonne.
  • Build-or-Borrow gate : platform-native > borrow > DIY, avec artefact-probe obligatoire avant d'écrire.
  • Estimation en tailles moteur (V12→I3), jamais en temps.
  • Skills : SKILL.md + sous-fichiers (progressive disclosure) + hooks + helpers SQL/python, gérés en dotfiles privés (stow).
  • Optimise pour le contrôle (contrat machine, fail-loud, critiques indépendants).

Même diagnostic (l'agent dérape sans rails), deux remèdes : Pocock pose des garde-fous légers et partageables ; nous posons des contrats stricts et vérifiés.

Le « grill-me » : la signature de Pocock

Pocock recommande la dictée vocale plutôt que le clavier pour tenir le rythme. grill-with-docs ajoute le Domain-Driven Design : il met à jour CONTEXT.md (langage ubiquitaire) et des ADR.

05« Smart zone » (tokens) vs « band moteur » (difficulté)

Les deux gèrent le même ennemi — la dégradation du modèle quand la tâche enfle — mais avec des unités différentes. Pocock raisonne en tokens de contexte ; nous raisonnons en difficulté d'ingénierie.

Pocock : la qualité chute bien avant la fin de la fenêtre annoncée → sessions courtes, resets propres

Pocock : performance fiable plafonnée « autour de 100k tokens quelle que soit la fenêtre annoncée ». Remède : tâches taillées pour tenir entièrement dans la smart zone, sessions courtes, /handoff pour repartir propre.

Nous : chaque tâche est calibrée I3 ou I4 (difficulté), une seule exception I6 (le contract task greenfield atomique). /next ne fait qu'une tâche par invocation puis STOP : le contexte ne gonfle jamais. L'état est dans la DB, pas dans le fil.

Convergence de fond : « petites unités indépendantes ». Divergence d'unité : tokens (mesure de contexte) chez lui, difficulté moteur (mesure d'effort, anti-temps) chez nous.

06Rules vs Skills : la même stratification

Distinction explicite chez Pocock, et structurellement identique chez nous : les rules disent comment se comporter sur la durée (toujours actives) ; les skills disent comment exécuter ce type de tâche (chargées à la demande).

07Où vit la vérité : spec vs état

Le clivage le plus profond. Chez Pocock, l'issue GitHub est à la fois le plan et l'état — un seul endroit, lisible, partageable. Chez nous, spec et état sont deux objets distincts, l'un versionné dans le repo, l'autre dans une base hors-repo.

Matt — GitHub comme source unique

  • to-prd → 1 issue GitHub (le PRD, « destination document » en prose).
  • to-issues → N issues grabbables (les slices).
  • L'état = statut de l'issue (open/closed, labels, assignee). Le sink est l'état.
  • Avantage : zéro infra, tout est dans GitHub, visible par l'équipe.
  • Coût : spec en prose, non validable par machine ; pas de versioning structuré du plan.
vs

Nous — spec ≠ état, séparés

  • SPEC : docs/plans/<slug>/plan.json — dans le repo, versionné, validé par read_plan.py.
  • ÉTAT : ~/mizraj/<slug>/progress.db — SQLite hors repo, machine d'état.
  • Sink Linear optionnel et lazy (via sink_id), jamais obligatoire.
  • Avantage : contrat machine, idempotent, co-client agent-cockpit.
  • Coût : plus d'infra (DB, validators, slug-derivation à synchroniser).

La forme exacte de notre spec

La machine d'état de notre exécution (/next)

stateDiagram-v2 [*] --> backlog backlog --> in_progress: /next implémente (working tree dirty) in_progress --> done: /next suivant = commit + push backlog --> blocked: spec manquante in_progress --> blocked: ambigu / revert blocked --> backlog: débloqué done --> [*]

Subtilité absente chez Pocock : /next ne commit jamais la tâche courante. Il laisse le working tree sale, et c'est le prochain /next qui commit+push après que l'humain a relu le diff. La revue du diff est le signal de validation.

08Vertical slices / tracer bullets : convergence totale

Point d'accord parfait. Les deux refusent les couches horizontales (DB → API → front en phases) au profit de tranches verticales fines traversant toutes les couches d'emblée, pour fermer la boucle de feedback dès la première tâche.

Chaque tranche traverse toutes les couches → 1 comportement observable, boucle de feedback dès slice 1

Pocock le dit comme ça

  • « thin tracer bullets qui coupent toutes les couches dès le départ ».
  • Issues organisées en DAG → travail d'agents en parallèle.
  • 1 issue = schema · API · UI · tests · e2e.

Nous le disons comme ça

  • « slice vertical : 1 comportement observable, jamais 1 fichier/1 couche ».
  • Milestones reliés par needs[] → tracks parallélisables.
  • Smell test : si les titres lisent comme un tour du codebase → re-slice.

10Enforcement déterministe : deux écoles du « pas-au-prompt »

Même conviction : une contrainte critique ne doit pas dépendre du fait que l'agent « pense » à la respecter. Elle vit dans du code qui bloque.

Matt — hooks Claude Code

  • git-guardrails : certaines opérations git exigent une validation humaine — full stop.
  • tdd actif : pas d'implémentation avant les tests — full stop.
  • setup-pre-commit : husky + lint-staged + Prettier + typecheck + tests au commit.
vs

Nous — hooks + validators + critiques

  • react-ts-gate : bloque any et as (sauf as const) à chaque Write/Edit.
  • Build-or-Borrow probe : artefact obligatoire avant d'écrire du code.
  • Critique de couverture (subagent Explore indépendant) + read_plan.py qui doit exiter 0.

Nuance : Pocock verrouille surtout des gestes dangereux (git, ordre TDD). Nous verrouillons en plus des choix de design (pas de any, pas de réinvention d'une feature native, couverture par surface prouvée).

12Convergences & divergences

Évolution convergente frappante : deux ingénieurs, sans coordination, arrivent au même squelette. Là où ça diverge, c'est sur l'arbitrage partage ↔ contrôle.

✓ Là où on est d'accord

  • Griller avant de coder — modèle mental partagé obligatoire.
  • Tranches verticales / tracer bullets, jamais des couches horizontales.
  • Skills = markdown composable + distinction rules/skills.
  • Hooks déterministes pour les contraintes critiques.
  • Deep modules (Ousterhout) pour la navigabilité par l'agent.
  • Discipline de contexte — petites unités, boucle de feedback courte.
  • Une étape de décomposition qui produit des unités « grabbables ».

✗ Là où on diverge

  • Spec machine (plan.json + DB) vs spec prose (issue GitHub).
  • Contrôle/traçabilité (critiques, validators) vs légèreté/partage (1 .md public).
  • Greenfield absolutiste vs (pas de règle anti-fallback explicite chez lui).
  • Difficulté moteur vs tokens comme unité de taille.
  • Linear opt. + SQLite vs GitHub comme tout.
  • Alignement en HTML interactif vs chat + dictée.
  • Livrables HTML brandés vs sortie markdown brute.

13Ce qu'on pourrait lui emprunter

Sans trahir notre doctrine (greenfield, contrôle), quelques idées de Pocock comblent de vrais trous chez nous. Estimées en difficulté.

  • [ ] Un skill diagnose dédié — boucle reproduce → minimize → hypothesize → instrument → fix → regression. On n'a pas d'équivalent formel. I4
  • [ ] Un mode caveman / compression — réduire la verbosité de l'agent (~75% tokens) sur les tâches mécaniques. I3
  • [ ] Un prototype jetable — répondre à une question d'archi par du code throwaway, hors pipeline plan.json. I3
  • [ ] Un zoom-out — contexte système large avant d'attaquer un codebase inconnu. I3
  • [ ] CONTEXT.md / langage ubiquitaire léger — un artefact de domaine plus simple que nos 6 champs pour les petits projets PME. I4
  • [ ] Option GitHub-issues-native — un sink alternatif à Linear pour les clients déjà sur GitHub. I6
