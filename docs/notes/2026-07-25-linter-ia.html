Étude · conception & faisabilité — v2

Un linter pour l'IA

Un moteur de règles déterministe, vraiment multi-langage, branché sur la frontière outil de l'agent — structure ET propreté du code.

Demande (précisée) — « Un outil de lint frontière-outil qui, contrairement à oxlint, joue sur deux points : règles de structure/fonctionnelles ET propreté du code, vraiment multi-langage (oxlint ne marche pas sous Astro ou JSON), de manière déterministe contrairement aux skills. »

Le produit exact n'existe pas : aucun outil ne combine règles AST custom multi-langage, couverture des fichiers pénibles (Astro, JSON, YAML) et règles de propreté déterministes, le tout accroché aux hooks d'un agent. Mais toutes les briques existent et s'assemblent : ast-grep comme moteur déterministe (JSON/YAML natifs, Astro via custom language + injections tree-sitter), des métriques par fonction en requêtes tree-sitter, et pour la propreté le pattern GPTLint (règles en langage naturel, deux passes LLM, cache par hash contenu×règle — exécution garantie, verdicts reproductibles). C'est un vrai trou dans le marché — les deux seuls projets OSS comparables sont dormants — et un MVP utile se construit en ~2 semaines sur ton setup.

01Spec du produit

Trois familles de règles, un seul point d'interception : le hook sur chaque Edit/Write de l'agent.

exemples

exemples

exemples

décidable par

Exigences transverses : multi-langage réel — TS/JS mais aussi .astro (frontmatter + template + scripts client), JSON, YAML, et demain n'importe quel fichier ayant une grammaire tree-sitter ; exécution garantie — le hook tourne à chaque écriture, pas « si le modèle y pense » ; règles ultra personnalisables — les tiennes, versionnées, pas le ruleset figé d'un vendor ; feedback immédiat — diagnostics renvoyés au modèle dans le même tour (exit 2 → stderr), pas en CI.

Distinction clé Pour la famille C, il faut séparer déterminisme d'exécution (la règle est évaluée à chaque fois — garanti par le hook) et déterminisme de verdict (même code → même diagnostic — à construire : cache, température, double passe). Les skills n'offrent ni l'un ni l'autre ; un linter-LLM bien conçu offre le premier totalement et le second à ~95 %.

ast-grep est la brique gagnante : ~25 langues built-in dont JSON, YAML, HTML, CSS ; règles YAML (pattern + relations + contraintes) ; et deux mécanismes d'extension décisifs — customLanguages (n'importe quelle grammaire tree-sitter compilée en lib dynamique, 4-5 lignes de config) et languageInjections (régions imbriquées parsées comme arbres indépendants : TS dans le frontmatter Astro, CSS dans un template literal). Pour .astro, la grammaire tree-sitter-astro existe (maintenue, mainteneur unique) — personne ne l'a packagée pour ast-grep : c'est exactement le trou que ton outil comble. Biome 2.3+ couvre bien Astro/Vue/Svelte mais avec ses règles ; Semgrep a ignoré les frameworks et son registry a un piège de licence (d'où le fork Opengrep).

03Règles de propreté par LLM : l'antériorité

L'idée « règle de lint écrite en langage naturel, évaluée par un modèle » a été prototypée deux fois en OSS — les deux sont dormants, mais l'architecture validée est réutilisable telle quelle.

GPTLint (MIT, dormant depuis 2024) est la référence architecturale : règles en markdown, pipeline deux passes (un classifieur repère les violations candidates, une seconde passe valide — tue la majorité des faux positifs), cache par hash fichier×règle (un fichier inchangé n'est jamais réévalué : coût borné, verdicts stables), température contrôlée, stats de coût affichées. Limité à JS/TS et jamais branché sur des hooks. Lintrule (2023, dormant) apportait l'autre bonne idée : évaluer sur le diff, pas le fichier — et documentait que les faux positifs LLM sont reproductibles, donc corrigeables en précisant la règle.

Le concept est validé commercialement en review-time : CodeRabbit combine précisément règles ast-grep custom + instructions NL par glob (leur billet s'intitule « AI-native universal linter : ast-grep + LLM ») ; Greptile apprend les règles depuis les commentaires de PR. Mais tous deux sont SaaS et interviennent au PR — trop tard pour ta boucle. Côté edit-time, agentlint (28 stars) branche 77 règles sur les hooks de Claude Code/Cursor mais en regex + délégation à ruff/eslint — pas de moteur tree-sitter universel. Enfin, Claude Code fournit déjà la primitive côté harness : les hooks acceptent des handlers prompt (évaluateur LLM single-turn, Haiku par défaut) et agent (subagent vérifieur) en plus de command.

Lecture Deux morts OSS + deux succès SaaS review-time + la primitive hook native = le créneau « edit-time, local, tree-sitter + LLM » est libre et dé-risqué. La leçon Vale (linter prose 100 % déterministe) : une grande part des règles « de propreté » se compile en checks A/B — le LLM ne doit juger que le résidu.

04Architecture proposée

Un CLI unique — appelons-le ailint — appelé par le hook, qui route chaque fichier vers trois moteurs et fusionne les diagnostics.

Les trois moteurs partagent la même fondation : les grammaires tree-sitter. Moteur A = ast-grep embarqué (built-ins + customLanguages : tree-sitter-astro, et demain TOML, SQL, n'importe quoi) avec languageInjections pour les fichiers composites — une règle TS s'applique alors aussi au frontmatter Astro et aux blocs script, gratuitement. Moteur B = requêtes tree-sitter sur les nœuds function_* (longueur, nesting, params) — trivial une fois les grammaires chargées ; la lib arborist-metrics (complexité cognitive par fonction, tree-sitter, Rust) est une base candidate. Moteur C = pattern GPTLint : règles markdown avec exemples bons/mauvais, évaluées par Haiku sur le diff, deux passes, cache par hash — jamais réévalué si contenu et règle inchangés.

La config est un seul dossier versionné de rule packs (par langue, par projet, partageables entre repos — le tien vivrait dans le stow). Sortie : diagnostics unifiés fichier:ligne — règle — message sur stderr avec exit 2, plus un mode --json pour la CI. Un hook Stop réutilise le même CLI en gate de fin de tour.

05Le problème dur : la propreté déterministe

C'est la seule vraie difficulté du projet — et elle se traite par dégradé, pas par miracle.

Premier réflexe : compiler tout ce qui peut l'être vers les moteurs A/B. « Pas de commentaire narratif » ≈ pattern AST sur les commentaires + heuristiques lexicales ; « fonction trop grosse » = métrique ; « pas de as, pas d'enum » = pattern. L'expérience Vale montre que le résidu réellement non mécanisable est plus petit qu'on croit — mais il existe (nommage par le domaine, altitude d'abstraction), et c'est précisément celui que les skills tiennent mal.

Pour ce résidu, le moteur C rend les verdicts quasi déterministes par construction : cache par hash (même contenu × même règle → même verdict, toujours — le non-déterminisme ne peut apparaître qu'à la première évaluation d'un contenu neuf) ; double passe (classifieur puis validateur — le pattern GPTLint qui écrase les faux positifs) ; règles avec exemples (chaque règle markdown embarque 2-3 cas ✅/❌ — c'est le rubric qui stabilise le jugement) ; portée diff (on ne juge que les lignes modifiées — coût et bruit bornés). Résultat honnête : ~95 % de reproductibilité, faux positifs reproductibles donc corrigeables en précisant la règle — incomparable avec le drift mesuré des skills (−5,6 %/fonction), et surtout exécution garantie à 100 %.

Garde-fou obligatoire Une règle C contestable + exit 2 = l'agent boucle en « corrigeant » du code correct. Il faut un circuit breaker (2 échecs sur la même règle+fichier → downgrade en warning non bloquant, pattern agentlint) et un niveau par règle (error bloque, warn informe).

06Pour / contre

Bilan du projet tel que spécifié, briques en main.

✅ Pour

  • Trou de marché réel : aucun moteur ne combine Astro + JSON/YAML + règles AST custom + hook edit-time ; les deux prédécesseurs OSS sont morts avant les hooks — le timing est bon.
  • Effort borné : les trois briques dures existent (ast-grep, grammaires tree-sitter, pattern GPTLint) ; le projet est un assemblage + une UX de règles, pas de la recherche.
  • Extension marginale par langue : une grammaire tree-sitter compilée + 5 lignes de config — là où oxlint/Biome exigent un support vendor.
  • Remplace la partie mécanisable des skills par du garanti, et rend le résidu de jugement exécuté à 100 % et reproductible à ~95 %.
  • Portable : mêmes règles sous Claude Code, Cursor (afterFileEdit), et en CI (--json).

⚠️ Contre

  • Distribution des grammaires custom : une lib dynamique par plateforme (pas de binaire portable) — le vrai coût d'ingénierie du multi-langage.
  • Les verdicts LLM ne seront jamais 100 % déterministes à la première évaluation ; il faut assumer le ~5 % et le circuit breaker.
  • Coût/latence du moteur C à chaque édition (mitigé : Haiku + diff seul + cache, mais non nul).
  • Maintenance des règles : chaque règle custom doit être testée contre les faux positifs sur le codebase avant d'être armée en error.
  • Grammaires framework jeunes (tree-sitter-astro : mainteneur unique ; tree-sitter-vue : précoce).
Boucle agent sur faux positif haut
Une règle C bruyante en exit 2 fait tourner l'agent en rond et brûle des tokens.
Circuit breaker 2-strikes → warning ; toute règle nouvelle naît en warn, promue error après une semaine sans faux positif.
Dérive de scope moyen
Vouloir couvrir 20 langues et 3 agents au MVP tue le projet.
MVP = ton stack (TS, Astro, JSON, YAML) + Claude Code seul ; l'extension vient après l'usage.
Coût LLM récurrent moyen
Moteur C sur chaque Edit d'une grosse session = appels Haiku en continu.
Portée diff + cache par hash + batch par tour (Stop hook) plutôt que par édition pour les règles C.
